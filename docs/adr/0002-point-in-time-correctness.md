# Family-loyalty and Mart 2 features must be recomputed as-of each row's visit date

`Extract_By_CSV.py` joins `tbl가족총매출` (가족총내방/가족총매출) as a single live snapshot, attached identically to every historical row for a family regardless of that row's own 내방일. We confirmed this empirically: for families with visits spanning >180 days, the value is constant across every row (n=1018 distinct-value-count-of-1 vs 0 elsewhere) — it's the current cumulative total as of extraction date (2026-01-16), not a historical time series.

Used as-is, this bakes look-ahead bias directly into Mart 1's training set: a 2023-dated training row would see 2025-level family loyalty as if already known in 2023. The 2yr/6mo/6mo temporal split exists specifically to prevent this kind of leakage, but a static snapshot join defeats it regardless of how the split is drawn. The same risk applies to Mart 2 (latest per-customer×drug consumption) whenever it's used to backtest Track 1+2's combined demand forecast on the validation/test period, rather than only at live production inference.

**Decision**: recompute 가족총내방/가족총매출 (and Mart 2, when used for backtesting) as of each row's own 내방일 — cumulative up to but excluding that visit — for both training and backtesting. The live current snapshot is legitimate only at actual production inference time, where "now" genuinely is now. This is a real trade-off (as-of recomputation is materially more expensive to build than a static join) accepted because the alternative produces a model that validates well in a leaky backtest and then underperforms in production — a train/serve skew that would otherwise surface late and be hard to diagnose.

**Update (implementing #4)**: 가족총내방 is recomputed as designed (`family_totals_as_of` in `pipeline/marts.py`, a count of distinct visits). 가족총매출 could not be: `raw_visits` (Extract_By_CSV.py's output) carries no per-visit monetary amount anywhere — only 소모량, a drug consumption quantity in units that aren't comparable across drugs, whereas `tbl가족총매출.총매출` is a genuine `money`-typed column with no per-visit equivalent extracted. Mart 2's as-of recomputation was implemented as designed, since it only depends on 내방일 and 소모량, both already present per visit.

**Update (closing #10)**: recomputing 가족총매출 point-in-time would have needed a raw-extract change first (a per-visit revenue/amount column joined from `tbl매출` or similar) — tracked in #10. Decided not to pursue it: 가족총내방 already captures family-loyalty behavior and is fully implemented, and the source-DB extraction work #10 would require outweighs the marginal signal a separate revenue figure adds. Mart 1 therefore uses 가족_총내방 (as-of) only; 가족_총매출 is permanently out of scope, not merely deferred.

**Update (implementing #11)**: `build_marts` (`pipeline/marts.py`) called `_chronic_customer_ids` — and the `revisit_match` matcher it wraps — on the *entire* `raw_visits` table, unfiltered by `as_of_date`. A visit dated after `as_of_date` could therefore make an earlier snapshot's classification "Chronic," leaking future information into Mart 1's inclusion filter, 만성질환여부, and Mart 3's Acute-Patient population routing — the one as-of-date gap `family_totals_as_of` and Mart 2's latest-consumption lookup didn't share. Fixed by pre-filtering `raw_visits` to visits with 내방일 <= `as_of_date` (`_visits_at_or_before`) before deriving `chronic_customer_ids`, at the `build_marts` call site — not by adding an `as_of_date` parameter to `revisit_match`/`_chronic_customer_ids` themselves. This keeps `revisit_match` directly callable exactly as it was (every existing direct call — `sample_mart1_weights`, `sample_mart1_negatives`, and this module's own tests — still gets the live/full-history classification it was built against), while `build_marts` is the only caller that now needs, and gets, the as-of-correct one.

**Update (wiring 학습_가중치/negative sampling into Mart 1)**: Two different call sites now need `sample_mart1_weights`, each with a different `raw_visits` population, deliberately: `build_marts`'s single-snapshot mart1 output passes it the same `_visits_at_or_before(raw_visits, as_of_date)` its own `chronic_customer_ids` already came from (via the new `_attach_mart1_weight` helper), keeping that snapshot fully as-of-correct end to end. The new `build_mart1_training_set` — which assembles Mart 1's full historical training set (Next-Day Visit positives plus `sample_mart1_negatives`' Y=0 rows, see that function) — instead passes the full, unfiltered `raw_visits`, matching the live/full-history-by-default precedent this ADR already established above for direct calls to `sample_mart1_weights`/`sample_mart1_negatives`. Re-deriving Revisit Match per distinct historical snapshot date across a full training set would be prohibitively expensive, and Chronic/severity status is being treated there as a population-membership decision for the training set as a whole, not a per-row leakage-sensitive X-feature. Only `build_mart1_training_set`'s per-row X-features (anchoring visit, family totals, MPR/no-show) are still recomputed per row's own snapshot date, via the same as-of-date helpers `build_marts` uses — that's the distinction point-in-time correctness actually protects here.

**Update (implementing #26)**: `build_marts` no longer re-runs Revisit Match on `_visits_at_or_before(raw_visits, as_of_date)`. Its Chronic population as of *d* is now every customer whose Chronic-since Date (`chronic_since_dates`) is ≤ *d*, per [[0005-lapse-aware-track1-population-and-evaluation]]. The as-of guarantee from the #11 update still holds: a match first observable after *d* can't make a customer Chronic as of *d*. Severity tiers are still derived from `_visits_at_or_before(raw_visits, as_of_date)`, as before. `revisit_match`/`_chronic_customer_ids` keep their unfiltered, live-snapshot behaviour for direct callers.
